# 83 — V1.1-LIFECYCLE-LOGGING-001 — Frozen implementation contract

**Status:** PLAN FROZEN; owner explicitly authorized implementation on 2026-10-16.
**Branch:** `architecture/dynamic-runtime-v2-discussion-freeze`. Backend READ ONLY.

## Source ownership
- ACTION: DynamicStore owns action start, rejection, execution success/failure/cancellation observation.
- DESTINATION: RequestActionHandler owns accepted backend-returned destination after the existing responseMode/retention requirements.
- NAVIGATION: ApplicationContent owns effect application, success/failure after NavigationState operations. No second navigator, preserve batch continuation and sanitized UI error handling.
- RENDER: DynamicRenderer owns identity/renderer checks and Compose commit signal; DynamicContainer owns entry-correlated reporting.

## Semantics
- Reuse existing Kermit and TraceContext; log only allowlisted event name, safe UUID identifiers, known action/operation classifications and outcome. Never log body, credentials, phone, OTP, device ID, URL, arbitrary payload or untrusted errors.
- HTTP success, destination resolution, navigation applied and composition committed are separate milestones.
- `render.committed` means Compose SideEffect after successful composition, **not** physical pixels rendered, media loaded or displayed to the user. Never mark rendering success solely because Render() was invoked.
- Handle missing screen or destination/template mismatch without fake success; avoid duplicate render commit events caused by recomposition.
- Cancellation propagates; diagnostics cannot change business behavior.
- Preserve existing action/result/effects, inert Sequence, State deferral, single navigation owner and current UI errors.

## Minimal source plan
1. Existing DynamicStore.kt: action start and terminal outcome, validation rejection; one safe Kermit tag.
2. Existing RequestActionHandler.kt: destination.resolved only after backend response destination is accepted.
3. Existing ApplicationContent.kt: navigation.applied/failed strictly after real effect operation result.
4. Existing DynamicRenderer.kt and DynamicContainer.kt: screen validation, renderer acceptance, one-shot Compose commit event and parent identity.
5. Existing feature/dynamic and app Gradle dependencies: Kermit reuse only if direct compilation needs explicit dependency.
6. Focused tests for correlation, missing destination, navigation state and render eligibility; owner runs JVM + Android/Web verification.

## Verification gates
No Kotlin compile or runtime success may be claimed from a remote GitHub commit. Require owner-side Gradle JVM tests, Android assembly, and Android Logcat, followed by source hygiene and documentation status update. Existing untracked local preview scripts and patches stay untouched.
